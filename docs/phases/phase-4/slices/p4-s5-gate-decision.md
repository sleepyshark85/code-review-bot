# P4-S5: See which findings would block a merge, per approved class

- **Status:** Done
- **Depends on:** P4-S1
- **Touches:** `governance.gate` (new), `governance.policy`, `pr.config`, `pr.carried` (new), `pr.runner`, `pr.shadow`, `pr.comments`, `pr.github`, `pr.rest_github`, `pr.fake_github`, `review`, `verify`

## Value
A repository that opts in sees which findings of a policy-approved class would block its merge: shadow reports say "would block", and in comment mode the summary says "blocks" and carries that state between pushes. No check enforces it yet ([ADR 0019](../../../adr/0019-merge-gate-from-the-bot-summary.md)).

## Acceptance criteria
Policy section `[[gate.classes]]` (`rule`, `min_severity` `high` or `critical`, default `critical`; `min_confidence` 0.5 to 1.0, default 0.9; `approved_by`; `approved_on`). Repository opt-in: `gate = [<class>, ...]` in `.review-bot.toml`. Which findings count, what carries, and the marker: [design, Merge gating](../design.md#merge-gating-appeal-and-override). Below, "money config" is a `.review-bot.toml` with `[[domain_rules]]` `rule = "decimal-money"`, `paths = ["billing/**"]` (severity default `high`) and `gate = ["decimal-money"]`; "the money class" is a policy class `decimal-money` (`high`, 0.9); a "trusted" summary is one the bot last edited, with a well-formed marker without ` tampered`.
- **AC1:** Given money config, the money class, and a shadow run whose PR adds `total = 9.99` at line 3 of `billing/prices.py`, then `shadow/v1` has `gate` `{"enabled": true, "decision": "block", "reason": null, "classes": ["decimal-money"], "blocking": [{"fingerprint": <16 hex>, "class": "decimal-money", "file": "billing/prices.py", "line": 3, "severity": "high"}]}`, and `shadow.md`'s summary says "Would block the merge: 1 finding (decimal-money)".
- **AC2:** Given a run that reads a `.review-bot.toml` with no `gate` key, or no `.review-bot.toml`, then `gate` is `{"enabled": false, "decision": "not_enabled", "reason": null, "classes": [], "blocking": []}`, the summary body and marker are byte-identical to Phase 3's, and the GitHub calls are exactly Phase 3's.
- **AC3:** Given `gate = ["decimal-money"]` under a policy that doesn't approve that class (the built-in policy approves none), or under the money class with no `[[domain_rules]]` entry for `decimal-money`, or only entries below the class's `min_severity`, then the run fails `invalid_config` with exit 2, naming the class, the reason and the policy's version, with no model call.
- **AC4:** Given the class `ai:security` (`critical`, 0.9), then a model finding with rule part `ai:security`, `critical` and 0.95 blocks; the same at `high`, or at 0.85, doesn't. A model finding tagged `decimal-money` (category `logic`) blocks under neither the money class nor `ai:logic`. Given AC1 with the run's threshold `critical`, then the `high` finding isn't reported and doesn't block.
- **AC5:** Given AC1's setup in comment mode: push 1 adds `total = 9.99` and blocks; push 2 changes only `README.md`, and the incremental run still blocks on it; push 3 changes the line to `total = Decimal("9.99")`, and the run has no blocker. A rule blocker's fingerprint is the one in the marker of the bot's inline comment on it, also after an identical line above it is removed.
- **AC6:** Given `possible-secret` enabled, then each line the whole base...head diff adds holding a secret hit blocks every run, as `critical`, confidence 1.0, with its new path and line (`line` null if its hunk header has no readable start). A file whose new path holds a possible secret blocks once, with `file` and `line` null, listed as "a file path holding a possible secret", and its lines add no further blockers. A hit only on a removed or context line, or only in an old path, doesn't block. No value or secret-holding path appears anywhere. When a later push removes the secret, the next run has no such blocker.
- **AC7:** Given comment mode and a blocker, then the summary says "Blocks the merge" and lists each blocker by file, line and class. It says how to appeal (reply on the thread) and how a maintainer overrides: `/review-bot override: <reason>` on the bot's thread, or, for a blocker with no thread of the bot's (a secret, a withheld finding, or a comment that is gone), a PR review whose body starts `/review-bot override <fingerprint>: <reason>`, with each such blocker's fingerprint shown. Its marker lists each blocker with its class.
- **AC8:** Given an `ai:` class, a trusted previous summary listing `ai:` blockers A, B and C, where A has the bot's inline comment, B was withheld and C's comment was deleted, when an incremental run reports nothing new: if A's comment is open, or a person resolved it, A still blocks; if the bot resolved it because its anchored line is gone, A is dropped. B and C block until a maintainer overrides them (S10), listed by fingerprint as "carried from an earlier review, no comment". A listed rule or secret blocker that this run's whole-diff checks don't find is dropped; if those checks couldn't run (AC11), every listed entry is carried.
- **AC9:** Given a previous summary that isn't trusted, a bot issue comment last edited by someone else (such as a summary whose marker is no longer its last line), or no summary with a readable marker while the PR has the bot's inline comments, then nothing is read from the marker, `reviewed=` included, so the run reviews the whole base...head diff. The same run rebuilds the carried `ai:` blockers from the bot's inline comments of enabled classes that are open or person-resolved, whose shown severity and confidence meet the class's minimums. If none of the bot's inline comments was last edited by someone else, and the whole-diff checks ran, the rebuild is done: the run decides with them as carried and writes no ` tampered`. Otherwise the decision is `block`, reason `tampered`, with the rebuilt blockers, and the marker gets ` tampered`, so the next run tries again. A withheld `ai:` blocker, or one whose comment was deleted, can't be rebuilt and is lost; the summary says a tamper occurred.
- **AC10:** Given a blocker of this run whose comment is withheld (`over_limit`, `not_commentable` or `possible_secret`), then it still blocks, and the summary names it by file and line.
- **AC11:** Given gating enabled, then by outcome:
  - `reviewed` (`no_new_changes` included): `pass` or `block`; `reviewed=` becomes the head unless a GitHub call failed (as in Phase 3). `skipped` `already_reviewed`: decided the same way, keeping the previous summary's body and rewriting only its gate section and marker.
  - `failed` with a provider category, `degraded` (S8), `blocked_secret`, and `skipped` for `too_large`, `nothing_to_review`, `empty`, `not_a_diff` or `unreadable`: `block` if any blocker is found, else `unjudged`, never `pass`; `reviewed=` is kept. Whole-diff checks run whenever the whole diff was read within `max_diff_bytes` and parsed; otherwise a trusted marker's entries all carry (AC8).
  - In comment mode, the runs in the two groups above write the summary, skips included, so "a skip edits nothing" (Phase 2) holds only with gating off.
  - Refused (fork, action, draft, `no_credential`), `missing_commit`, and `failed` `invalid_config` (AC3 included) never read a valid config: `gate` is `{"enabled": null, "decision": "unjudged", "reason": "no_config", "classes": [], "blocking": []}`. When `pr run` has `REVIEW_BOT_GATE=on`, or the previous marker has `gate=`, `more=` or ` tampered`, they neither create nor edit the summary (so no `summary written` step runs); otherwise they write as Phase 3 does.
- **AC12:** Given any run that reaches a decision (a run that ends on a GitHub or git error writes no report, as in Phase 3), then the audit log has one `policy`/`gate` record with `enabled`, `decision`, `reason`, `classes`, `fingerprints` (every blocker's) and `policy_version`.
- **AC13:** Given a policy class `swallowed-exception` or `open-without-encoding`, then the policy is invalid (exit 2), naming the class and saying its rule reports only `medium` (or `low`), so it can never block.
- **AC14:** Given a trusted previous summary, but any of the bot's inline comments last edited by someone else, then the decision is `block`, reason `tampered`, the carried blockers are kept, and the marker gets ` tampered` (so the next run takes AC9's path).

## Limits
The marker lists at most 25 blockers, `ai:` ones first, then most severe first; `shadow/v1` and the audit record list all. Beyond 25 the summary states the total, the decision is `block`, and the marker says how many it left out. Accepted and disclosed: `ai:` blockers beyond the 25 listed aren't carried, unless the model reports them again, and the summary says how many. The summary stays under 60,000 characters. The marker is untrusted, read up to 2,000 characters; any part out of the [grammar](../design.md#interfaces) makes it malformed (AC9). Whole-diff checks are linear in a diff read within `max_diff_bytes`; an incremental run reads two such diffs. A PR with no summary and no bot comments whose whole diff can't be checked is `unjudged`: it fails open, as [Q5](../design.md#6-open-questions) accepts (with bot comments, AC9 applies). Accepted and disclosed: if the summary is deleted on a PR whose only `ai:` blockers were withheld, the next run sees no bot comment, reviews afresh, loses them, and reports no tamper.

## Interfaces
`RepoConfig.gate: tuple[str, ...]`. A class is a `RuleId` other than `swallowed-exception` and `open-without-encoding`, `ai:<category>` or `possible-secret`. `GateDecision`: `not_enabled`, `pass`, `block`, `unjudged`. `gate.reason`: null, `tampered` or `no_config`. `REVIEW_BOT_GATE` (`on`, `off` or unset) is read by `pr run` only for AC11's last case; any other value is a config error, checked on every run (exit 2), as in `check-mode`. Marker: [design, Summary marker](../design.md#interfaces).

## Out of scope
- The check that enforces it, and overrides (S10); approving classes (S11; the owner).
