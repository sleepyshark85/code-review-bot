# P4-S10: Block a merge with a required check, with appeal and override

- **Status:** Approved
- **Depends on:** P4-S5, P4-S9. **Merges only after** P3-S15 has added the Claude context suite and `.github/review-bot-policy.toml` lists `context` (P4-S9 AC9)
- **Touches:** `pr.gate_check` (new), `pr.cli`, `pr.github`, `pr.rest_github`, `pr.fake_github`, `governance.policy`; `.github/workflows/review.yml`, `docs/runbook.md` and `CLAUDE.md` (main session, from this spec)

## Value
A repository that gates gets a `merge gate` check. It fails while an approved-class finding blocks, passes when a maintainer overrides it with a reason, and never fails just because the model is down ([ADR 0019](../../../adr/0019-merge-gate-from-the-bot-summary.md)).

## Acceptance criteria
AC1 to AC9 run through `pr gate` over `FakeGitHubClient`, and AC10 and AC11 by parsing `review.yml`. Rules: [design, Merge gating](../design.md#merge-gating-appeal-and-override). Policy key `[gate] self_override` (bool, default false).
- **AC1:** Given the bot's summary, last edited by the bot, with `reviewed=<head>` and `gate=<A>:decimal-money` ([marker grammar](../design.md#interfaces)), and no override, when `pr gate --event E --out DIR` runs, then `DIR/gate.json` (`gate/v1`) has `decision` `block` and A's class, with its file and line from the bot's inline comment whose marker has A's fingerprint (or null, with "see the summary", when there is none), it exits 1, and stdout (the job summary) names each blocker and how to appeal and override.
- **AC2:** Given `reviewed=<head>` and no `gate=`, then `pass`, exit 0. Given gating not enabled (no `gate` in the base commit's `.review-bot.toml`), then `not_enabled`, exit 0. Given a base `.review-bot.toml` that is invalid, or whose `gate` names a class the policy doesn't approve (P4-S5 AC3), then the check decides from the summary as if gating were on, with `gate.json` `reason` `no_config` and stdout naming the config error, so listed blockers still block and a PR with none is `open`; the review runs left that summary unedited (P4-S5 AC11).
- **AC3:** Given a bot-edited summary with `reviewed` not the head and no `gate=`, or no summary on a PR for which no `review.yml` comment-job run wrote one, with no inline comment by the bot and no `--reviewed-sha`, then `open`, reason `not_reviewed_at_head`, exit 0, and stdout says the check passed without a review at this commit.
- **AC4:** Given any of these, then `tampered`, exit 1, naming the cause: a summary last edited by anyone but `github-actions[bot]`; a summary whose marker carries `tampered` or is malformed (P4-S5 AC9); an inline comment by the bot last edited by anyone else (P4-S5 AC14); or no summary although a `review.yml` comment-job run for this PR wrote one (that run's job list shows its `summary written` step, which runs only after the summary is written, as `success`; read from the Actions jobs API with `actions: read`, with no artifact download), the PR has an inline comment by the bot, or `--reviewed-sha` is given. A comment-job run that was refused wrote no summary (P4-S5 AC11), so it doesn't count. A deleted summary therefore can't open a PR whose only blocker is a secret or a withheld finding. Once a review run's rebuild succeeds (P4-S5 AC9), its new bot-edited summary, without `tampered`, is decided like any other.
- **AC5:** Given a reply on A's thread whose first line is `/review-bot override: retry is handled by the caller`, from a `COLLABORATOR` who isn't the PR's author, and last edited by that author or not at all, then `overridden`, exit 0. `gate.json` records for A the reply's comment ID and login, never the reason's text, and the audit log has the same as `policy`/`override`.
- **AC6:** Given a blocker S with no inline comment of the bot's carrying its fingerprint (a secret, a withheld finding, or a comment that is gone), then the override is a submitted PR review whose body's first line is `/review-bot override <S's fingerprint>: <reason>`, under AC5's other conditions. Its `pull_request_review` event runs the gate on the PR's head. A thread reply never covers S, a review naming a blocker that has a bot thread doesn't count (stdout says to reply on the thread), and a plain PR comment never counts.
- **AC7:** Each of these is ignored, and stdout says why: an override from the PR's author unless `self_override` is true; one from an association of `CONTRIBUTOR`, `FIRST_TIME_CONTRIBUTOR` or `NONE`; one with a reason under 10 or over 500 characters; and one last edited by anyone but its author.
- **AC8:** Given blockers A and B with only A overridden, then `block` on B. Given a later push that still has A, then A's override still holds, because it covers the fingerprint for the rest of the PR. Given a marker with ` more=5` and every listed blocker overridden, then `block`, and stdout says 5 blockers aren't listed and can't be overridden until fewer remain.
- **AC9:** Given a `pull_request` event of any action, a `pull_request_review_comment` event or a `pull_request_review` event, then the PR is read from it. For the comment and review events, `pr gate` then checks that the PR's head repository is this repository, and otherwise ends `not_enabled`, exit 0, with nothing read. Any other event, or an unusable file, exits 19. A GitHub API failure exits 18: the check fails visibly and passes on a re-run, never open.
- **AC10:** Given `review.yml`, then a job `merge-gate`, named `merge gate` (never `gate`), runs on `pull_request`, `pull_request_review_comment` (`created`, `edited`, `deleted`) and `pull_request_review` (`submitted`, `edited`, `dismissed`), never on `issue_comment`, only when `REVIEW_BOT_MODE` is `comment` and `REVIEW_BOT_GATE` is `on`. For `pull_request` events its `if:` also requires a same-repo head, as today's jobs do; for the other two, `pr gate` checks it (AC9). It runs after `check-mode` and the comment job with `if: always()`, and passes the comment job's reviewed head as `--reviewed-sha`. Its permissions are exactly `contents: read`, `pull-requests: read` and `actions: read` (read-only, to find the comment job's runs, AC4). It gets no model key, gets `GITHUB_TOKEN` only in its gate step, installs from the base commit, and uploads `gate.json` and its audit log for 90 days. Its concurrency group is keyed by PR number **and** `github.event_name`, with `cancel-in-progress: true`, so a reply or review never cancels the `pull_request` run's gate job.
- **AC11:** Given `review.yml`, then `check-mode`, `shadow`, `comment` and `collect` run only when `github.event_name == 'pull_request'`, and are otherwise unchanged, so a review-comment or review event starts no review and cancels none. `check-mode` also rejects any `REVIEW_BOT_GATE` other than unset, `off` or `on`, and fails with one error naming the policy when `REVIEW_BOT_CONTEXT` is `repo` but the policy's model entry lacks `context`. Both review jobs pass `--policy .github/review-bot-policy.toml`, and the comment job passes `REVIEW_BOT_GATE` to `pr run` (P4-S5 AC11). The comment job ends with a step named `summary written` that runs only when the run wrote the summary (AC4).
- **AC12 (recorded):** Once the owner turns the gate on, a person confirms on test PRs that a blocker turns the required check red on the PR's head commit, and that both override paths turn it green there: a thread reply for a finding, and a submitted review for a test secret (a fabricated value in a format the scan reports, never a real key, on a PR closed unmerged). The test report records the PRs, the head SHAs and the runs.

## Limits
Replies, reviews and the summary are untrusted; the summary's marker is parsed under P4-S5's limits and grammar, and anything else is `tampered`. At most 100 replies are read per blocking thread, 25 threads per run, 500 PR reviews, 100 workflow runs and their job lists. Run and job data expire under GitHub's retention, after which a deleted summary falls back to `open` (P4-S15 AC6). The override line is matched exactly at the start of the first line, case-sensitive. Logins are shown escaped and capped at 100 characters.

## Interfaces
`python -m review_bot.pr gate --event PATH --out DIR [--policy PATH] [--reviewed-sha SHA]`: exit 0 (`pass`, `overridden`, `open`, `not_enabled`), 1 (`block`, `tampered`), 2, 18 or 19. `gate/v1` `reason`: `not_reviewed_at_head`, `no_config` or null. `GitHubClient` adds, beyond P4-S5's last editors, `read_summary_state(pr)` (the body and the last editor's login), `list_replies(pr, comment_id)` and `list_reviews(pr)`, each giving ID, login, association, body and last editor; and `has_comment_job_run(pr)`, true when a `review.yml` run for the PR has a successful `summary written` step, from the Actions jobs API.

## Out of scope
- Making `merge gate` required, and setting `REVIEW_BOT_GATE`: the owner.

- **Runbook (main session):** "Appeal and override a blocked merge": what the author does (reply on the thread, and the owner is notified), who may override and how, what is recorded, how to remove a class from the policy if overrides pile up, and that agents never post overrides. It also gives the way out of a PR stuck in `tampered`, which is the simpler option chosen over having the bot restore deleted comments: a maintainer inspects the PR's history and the gate's `gate.json`, then either merges with an admin bypass, recorded in an issue labelled `review-bot` with the reason, or closes the PR and opens a new one from the same branch, which gets a fresh full review.
- **CLAUDE.md (main session):** a rule that no agent or main session posts `/review-bot override` replies or comments; only a person does. A matching deny rule in `.claude/settings.json` is the user's to add ([design §4](../design.md#4-needs-a-person)).
